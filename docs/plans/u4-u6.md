## 1. Order and rationale

**Recommended order: U4 (rules) -> U5 (dice) -> U6 (authz).**

1. **Dependencies point that way.** `dice::compose` and the `Roll`/check,
   `SpendHitDie` and `CastSpell` handlers consume U4's frozen `RollParts`/
   `DiceTerm`/`RollHint`; U6's pre-check wraps U5's `Executor::execute_as`
   and consumes U5's `Command` variants and `Environment` error. Reversing
   U4/U5 splits the seam across units; reversing U5/U6 would authorize a
   command surface that does not exist yet.
2. **Smallest blocking decisions first.** U4 and U5 each have exactly one
   skeleton-blocking Open Question (`rules.md` OQ-1: leave U3's formula-max
   paths as built, recommendation A; `dice.md` OQ-1: environment ports stay
   defaulted `CommandEnv` methods, recommendation A). `authz.md` has none.
   Settling the two reviewer calls unblocks all three skeletons.
3. **The target-test compile ladder matches the order.** `rules_target.rs`
   needs only `localtt_engine::rules`; `dice_target.rs` needs U4's types,
   U5's modules, the adapter RNG and the U5 command additions; `authz_target.rs`
   needs everything above plus U6's two modules. Each skeleton is the first
   phase where its test compiles, and each test then fails at `todo!()`.
4. **The workspace gate is only fully green at the end either way.** While
   any unit still carries `todo!()` bodies, `just lint` stays red
   (`clippy::todo`) and `just test` stays red; the order above makes the
   longest-running red window the shortest it can be.

Not recommended: U5 before U4 (the dice skeleton would declare half a seam and
the check path could not be written), or U6 before U5 (the pre-check has no
`execute_as` to live in).

nobody edits them silently afterwards.

Shared constraints for all three skeletons:

- **No core edits.** A wire gap becomes a versioned proposal (the authz OQs
  and the U4 deferred items list the candidates); skeletons never touch
  `localtt-core`.
- **No edits to frozen artifacts.** `engine_target.rs`, `store_target.rs`,
  `content_target.rs`, `scenarios.rs`, `properties.rs` and the U1--U3 docs
  stay byte-identical. `just fmt` before every commit (see 7.3).
- **Docs deny `missing_docs`.** Every declaration lands documented; that is
  the one lint obligation a skeleton must satisfy.

## 3. Per-unit work

### 3.1 U4 -- rules

**Skeleton declarations** (all bodies `todo!()`):

- `crates/localtt-engine/src/rules/{mod.rs, formula.rs, collect.rs, armor.rs,
  tables.rs}` per `rules.md` section 6; `lib.rs` gains `pub mod rules;`.

  `RulesContext`-based output types, `DerivedSheet`, `DerivedValue`,
  `DerivedResource`, `Contribution`, `ContributionSource`, `ContributionOp`,
  `SlotMaxima`, `PactSlots`, `RollHint`, `RollParts`, `DiceTerm`.
- `commands::rests` long-rest recovery (HP, death saves, exhaustion per
  `rules.md` 5.10/D7) is declared or left untouched exactly as `rules.md`
  pins; `rules_target.rs` is the first test to compile.

**Implement slices (spike first):**

1. **Spike:** `derive` over the golden party for one stat (`ability_mod.*`)
   through `formula.rs` plus one collection path and one override, making a
   single target assertion green end to end.
2. Static formula matrix (`formula.rs`), including dice-in-static-context with
   `DiceInStaticContext`.
3. Modifier collection: conditions (equipped/attuned/status/custom), groups,
   labels, warning scoping (`collect.rs`).
4. Pipeline staging per key: `Set`, `Add`, `Min`/`Max`, advantage/
   disadvantage cancellation, `DerivedValue.hint` (`rules.md` 5).
5. Armor and AC bases, over-armor and strength warnings (`armor.rs`).
6. Class tables: proficiency, multiclass slots, pact magic, hit-dice pools,
   `UnmodeledClass` (`tables.rs`, OQ-2 of `rules.md` recommendation A).
7. Resources and `DerivedResource`; overrides (`override_value`,
   `effective`).
8. `roll_parts`: dice extraction, `Malformed` edges, the U4/U5 seam.
9. Long-rest recovery arithmetic in `commands::rests` (OQ-5 split; engine
   unit tests, no target coverage).
10. Engine unit tests beyond the target suite (full formula matrix, group and
    condition tables, AC tie-breaks, staging/order/scoping edges, duration
    expiry, recovery arithmetic; `rules.md` 6), then the target suite green.

**Closure:** `rules_target.rs` green; frozen suites untouched; U5 can start
consuming the seam.

## 6. Gate story per phase

The batch spans three phases per unit; the gates tell the truth at every step
(arch section 10: skeleton noise is expected, implement must be clean).

**Spec (now, after this plan).**

- `just fmt`: green (the U4/U5 tests were formatted in `50119b1`; the U6
  commit is fmt-clean).
- `just check` (`cargo doc` + feature powerset): expected green -- it does not
  build test targets.
- `just lint` and `just test`: red, because the three spec targets do not
  compile (unresolved pinned API). That is the spec-phase contract, recorded
  in the final report rather than papered over.
- The frozen suites stay green individually: `cargo test -p localtt-engine`,
  `cargo test -p localtt-adapter`, and the U1--U3 integration targets
  (`engine_target`, `store_target`, `content_target`, `scenarios`,
  `properties`).

**Skeleton (per unit).**

- Declarations compile: `cargo check -p localtt-engine` and the unit's target
  `cargo check -p localtt-integration --test <name>` pass.
- The unit's target test runs and fails `not yet implemented`; earlier target
  tests keep their previous state (see section 4).
- `just lint` is red on `clippy::todo`, unused parameters and dead code. Arch
  section 10 declares this expected for the skeleton commit; it is not a gate
  failure yet, but it must not be silenced with `#[allow]`/`#[expect]`.
- `just test` stays red while any skeleton is unimplemented.
- No frozen artifact and no core file is modified.

**Implement (per unit).**

- The unit's target suite is green
  (`cargo test -p localtt-integration --test rules_target`, `--test dice_target`,
  `--test authz_target`), plus the engine/adapter unit tests the unit added.
- Previously implemented units stay green; `just fmt` ran before every commit.
- Workspace `just lint`/`just test` may stay red while later units still carry
  `todo!()` bodies; no new warnings in touched files.

**Batch end (after U6 implement).**

- `just lint`, `just check`, `just test` are all green; that state is what CI
  gates on and what the batch review claims.

Never in any phase: skipping or weakening a check, editing a frozen target
test to pass, or silencing lints except with a documented reason.

## 7. Risks and unknowns

1. **Blocking Open Questions are settled (A).** The 2026-10-18 adversarial
   review resolved `rules.md` OQ-1 and `dice.md` OQ-1 to recommendation A:
   U3's rest paths and the `CommandEnv` ports stay exactly as built, and every
   frozen test stays byte-identical. B remains a post-batch route; choosing it
   later needs the affected target tests and RFCs rewritten first.
2. **A long red-gate window.** `just lint`/`just test` cannot go green until
   the last `todo!()` is implemented. The branch must not be proposed for
   merge mid-batch; the spec report records the red state explicitly.
3. **Formatter drift.** The U4/U5 commits were not fmt-clean under the
   floating nightly (`rustfmt 1.10.0-nightly`, no pinned toolchain); `50119b1`
   fixed it. Run `just fmt` before every commit; pinning the toolchain is a
   tooling decision outside this batch.
4. **Target tests are a floor, not a ceiling.** Each RFC section 6 lists the
   engine unit tests the implement phase owes; skipping them because the
   target test is green would leave the exact edges (caps, tie-breaks,
   saturation, regain arithmetic, mask algebra) unpinned.
5. **Exhaustive matches are intentional breakage.** U6's command classifier
   and `ViewField` map match exhaustively; a future command or core field
   fails compilation until the new case is decided. That is the design; the
   fold into decisions should say so.
6. **`list_entities` infallibility.** The pinned signature skips an
   unresolvable header instead of surfacing a store fault. It cannot happen
   while the working set is consistent; if a future store fault should
   surface, that is a signature change and a target-test review event.
7. **API drift after freezing.** Any later edit to a frozen signature means
   editing a committed target test; treat it as a review event and re-run the
   affected `cargo check --test`.
8. **Fixture catalog overstatement.** `localtt-integration/DESIGN.md` lists
   pieces the golden cast does not carry (Hex, armor, slots); the target tests
   add them locally. The catalog update is on the after-acceptance list.
9. **Dependency risk (low).** U5 adds `rand_chacha` for `ChaChaRng`; if the
   registry or pin is unavailable, the target test's seed-replay assertions
   and the adapter module block. Verify with `cargo add` at the U5 spike.
10. **No concurrency surface.** The engine stays synchronous and
    single-writer; no loom/shuttle work is owed by U4--U6.
